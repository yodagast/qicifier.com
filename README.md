# 浙江产业带企业库（zanzhu.vip）

参照 [河北工厂网](https://hebei.mengkai.ren/) 的数据方法，把浙江的「块状经济」做成**可检索、可核验、可直连**的产业带骨架。
方法论见 [docs/浙江产业集群收录体系搭建方案.html](docs/浙江产业集群收录体系搭建方案.html)。

技术栈：**Vue 3 + Vite**（前端）· **FastAPI + SQLAlchemy 2.0**（后端）· **PostgreSQL**（数据库）。

### 调研清单的 C 档：照常展示，但标签必须降级

两份调研清单的「可用范围」一栏原本写着 C 档「不可对外展示；仅作内部待核清单」。
**站方决定不采纳这条限制**：C 档线索照常展示，可信度靠**逐字段标签**交代，而不是靠隐藏。

| 档位 | 判定 | 页面标签 |
| --- | --- | --- |
| A 官网公示 | 官网联系页/页脚可核到电话与地址 | 第三方调研 · 官网公示（未复核） |
| B 官网可核 / 工商可核 | 有官网但电话未公示，或仅工商登记 | 第三方调研 · 工商可核 / 官网可核（电话待补） |
| C 第三方线索 | 仅来自第三方目录或行业报道，未核验 | 第三方调研 · 未核线索 |

**为什么不做可见性开关**：一旦「同一批线索有的能搜到、有的搜不到」，
用户没有任何办法知道差别在哪，检索结果也就不可解释了。
标签是逐字段的，所以「官网来自调研、电话来自第三方目录」这种混合来源能被如实呈现。

## 第三方调研清单怎么进库（以武义户外运动与休闲为例）

一份外部调研清单和官方名单走的是同一条代码路径，但**核实程度必须分开**，否则「官方认定」
这个标签就没意义了。导入时守住四件事：

1. **来源文件逐字留档**：`data/source/wuyi_outdoor_2026.csv` 原样保存，解析断言写在
   `tools/parse_outdoor.py` 里（行数、序号连续、档位分布 7/10/48）。
2. **核实程度按名单分级**：`SOURCE_FILES` 不只是文件清单，它同时把每个来源映射到
   `official` / `site_curated`。荣誉列表（`honors`）按名单查表决定档位——
   以前这里把所有名单都盖成「官方认定」，接进调研清单后会变成把调研清单说成工信部认定。
3. **逐行保留调研方的核实档位**（`verify_tier`）：同一份清单里 A 档是官网公示、C 档只是
   第三方目录线索，差得很远。联系方式标签也**逐行降级**，不共用一层标签。
4. **调研方给的官网只当候选**：写进 `data/curated/research_sites.json` 后，和别的候选一起
   过**同一道验收门**。这次 65 家里只有 3 家的官网站住了（如 `cn.oasischina.com`），
   它们以「站方核验 · 已比对官网」入库，比调研层的「未复核」更可信；
   没站住的（例如 `sunshinecn.cn` —— 调研方自己也在备注里写了「官网页脚署名与工商名称不一致」）
   就留在调研层，页面明确标未复核。

**CSV 里的哨兵值必须先丢掉**。这份清单 65 行里只有 9 行有真官网，其余是
`未获取` / `无官网（一比多商铺页）` / `官网为占位符`。这些字符串如果当成数据进了库，
页面上就会出现一批**看起来有官网**的企业——这是最难被发现的一类污染，所以解析器在入口就拒绝，
并在测试里断言「全库没有任何哨兵值出现在 website / phone 列」。

顺带修掉的两个隐私/准确性风险：

* 清单里有两家标着「A 官网公示」，电话栏填的其实是**老板的手机号**（`153…` / `137…`）。
  解析器按全站边界拒绝个人手机号，并在备注里写明「电话未收录：手机号（本站不采集个人联系方式）」，
  页面才不会看起来像漏填。
* 地址列有 `武义县` 这类过粗的值、以及 `未获取`，一并丢弃（地址要落到街道/园区/门牌才有检索价值）。

### 品类专属规则：调研清单比我们更懂自己的品类

《全国无缝服装企业调研清单》在通用分档之外补了两条品类规则，本站的处理方式：

| 清单建议 | 本站做法 | 理由 |
| --- | --- | --- |
| 地址拆成「注册地／办公地／厂址」三个字段，因为知音纺织、伊秀服饰在自家官网上给出了两个地址 | 实现为 `address`（对外展示的官网地址）+ `address_registered`（工商注册地，仅在与展示地址不同时填）+ 备注里写清两处来源 | 只存一个字符串，无论存哪个后续都会被质疑；但「厂址」这一档本次没有任何数据，为它单开一个恒为空字段没有意义，先不建 |
| **手机号按「性质」判断**：官网公示的招聘专线/客服热线保留并标注性质，具名的个人手机号剔除 | **不采纳**。手机号一律不收录，但把它们的存在与性质写进备注 | 见下 |

**为什么手机号这条没有采纳。** 两份调研清单对同一件事给了相反规则——武义那份写
「剔除所有个人手机号」，无缝服装这份改成「按性质判断」。本站已经公开的边界声明是
「手机号一律不采集、不展示」，这是一条承诺，不能为了让 A 档多两条电话而悄悄放宽。
而且「招聘专线」与「个人手机」在页面上很难稳定区分：天派针织那条既是招聘专线、
也是一个 173 段的个人号段。所以处理方式是**不收录，但不装看不见**：

```
电话未收录：官网仅公示手机号（原文「+86 17336769979」），按本站边界不采集手机号
```

这样采购商知道「不是没有电话，而是我们按边界没登」，不会以为清单漏填。
若要改为清单建议的口径，需要同步修改 `/about` 的边界声明，属于对外承诺变更。

### 无缝服装清单的修订版（137 行）：合并，而不是覆盖

同一份《全国无缝服装企业调研清单》先后给过两版：首版 `docs/全国无缝服装企业清单.csv`
（19 家，带「主营产品」列）与修订版 `docs/全国无缝服装企业调研清单.csv`
（**137 行**，第一批，改成工商底表口径：官网类型/电话性质/地址类型/核实等级）。

修订版**不是**首版的超集：14 家重合（其中「奥丽侬」的登记名从 `奥丽侬集团` 变成
`奥丽侬集团（广东奥丽侬内衣集团有限公司）`、「博尼」从集团名变成工商名
`浙江博尼时尚控股集团有限公司`），另有 5 家只在首版里出现。所以两版是**并集**存档，
不是覆盖：

| | 处理 |
| --- | --- |
| 首版 19 家 | **原样保留**（`data/source/seamless_garment_2026.json`，内置名单）—— 它仍是一份独立清单 |
| 修订版 137 行 | 走 `/api/admin/lists/import`，`source_key=seamless_research`（`data/source/seamless_research.json`） |
| 首版独有的 3 家（幂姿内衣/博鑫服饰/博尼国际） | 并进修订版的**联系方式层与候选官网层**（同一份名单的同一层不该有两份文件），主体仍在首版那份里 |
| 同一家公司名在两版都用 | 联系方式取优先级更高的一层；`list_names` 两条都记 |

**由此暴露并修好的一个真 bug**：首版里「博尼国际控股有限公司（浙江博尼时尚控股集团）」、
「曼妮芬（义乌分公司）」、「幂姿内衣（佛山南海盐步）」这类名字，`match_name` 规则
（剥掉**结尾**括注）会把括注当股票代码/品牌名剥掉，得到「博尼国际控股有限公司（浙江」
这种半截名字，而且**整条企业记录的其余字段会被清空**（`match_name` 为空、`note` 空、
`verify_tier` 空、`cluster_slugs` 空）。修法是：只剥**看起来像补充说明**（股票代码/品牌名）
的括注，括注里出现「公司/集团/厂/研究院」这类**主体字样**时说明它是法定名称的一部分，原样保留。

> 这类 bug 不会报错，只会让页面上的字段莫名其妙地空着。修订版把名字换成工商登记名后
> 它依然存在（集团名与工商名同时收录），所以是新增的 `list_names` 合并逻辑把它逼出来的。

### 「产区」列：一份清单里好几个产区

修订版把首版的「浙江义乌 / 广东汕头」这种**粗粒度产区**细化成
「义乌无缝针织 / 汕头谷饶针织内衣 / 汕头潮南内衣 / 佛山盐步内衣 / 晋江深沪内衣 /
浦江针织服装 / 其他产区」——**地方 + 品类**，并带省内外之分。这带来三件事：

* **接口导入器原本读不懂这一列**（它只认「块状经济」那种逐行独立的产区名），
  137 行会全部挂不上集群；而接口是 README 推荐的官方路径。所以把映射补进
  `list_import.PRODUCTION_AREA_INDEX`，并把「用了哪一列」记进 `list_cluster_basis`。
* **省外产区会被当成浙江企业**：`geocode_row` 的判据是「有行政列就信列」，而它判断
  「是不是浙江」用的是地址文本 —— 这份清单的地址栏写的是门牌（「钟潭竹园93号」），
  不含省市名。于是「揭阳市」「苏州市」一路顺风地被算进浙江。两道判断补上：
  清单标了省外产区就标省外；没标时看**地市名**在不在浙江 11 市里。
* **多出两个产区需要建档**：`汕头潮南内衣`（省外对比产区）与 `浦江针织服装`
  （省内调研产区，官方第四批名单里没有它）写进 `research_clusters.json`。
  潮南与谷饶分开建档：谷饶在潮阳区、以无缝代工为主，潮南以一线的品牌内衣
  （家居服/文胸/内裤）为主，合成一条会把两类实体混进同一张表。

**「其他产区」7 家刻意不挂集群。** 那是作者自己写的「别处」（揭阳普宁、湖州南浔、
德清、东阳、海宁、诸暨、昆山各一家），**不是我们没认出来**，所以：
不报「未识别」warning（`NON_AREA_VALUES` 与 `unknown_production_areas` 分开计），
不替它猜一个产区。其中 5 家落在浙江某个有主导集群的镇街（南浔镇、武康街道、横店镇、
海州街道、大唐街道），会被全站既有的**兜底规则**归入那个镇街的主导集群并标
「归属待确认」；剩下 2 家在浙江之外（普宁、昆山），连兜底都没有。
报告与测试都钉住了「7 家不挂无缝产区、2 家完全没有归属」这两个数。

**归属怎么做。** 58 行自带「块状经济」列，全部命中已有的镇街级产区（大陈衬衫、嵊州领带、

与「全国代表企业」批次同一做法（那 7 家「集群代表企业」本来就是长兴协同区的代表）。

为此给导入器加了**整份清单的归属声明**（`default_cluster_slug`）：

| | 处理 |
| --- | --- |
| 逐行自带依据（块状经济列 / 产区列 / 集群类型列） | **优先**，它比「整份清单都在这一条赛道上」更具体 |
| 整份声明 | **兜底**，只在本行没有任何依据时才生效 |
| 认不出来的整份 slug | **422 挡住**。几百行的归属一旦指向不存在的集群就会静默挂空 —— 页面只是少了归属，不报错，所以宁可导入失败 |
| 转发 | 声明也写进注册表（`default_cluster`），来源声明里因此说得清「这几百家为什么都挂同一条赛道」 |

**省外 172 家照收，但必须能被拆开。** 本库是浙江产业带库，把省外样本混进「浙江企业数」
等于换个方式说谎，所以这 172 家标 `out_of_province`、单独计数、不挂浙江行政区。
`415X-现代纺织与服装` 这条赛道因此从 **31 家撑到 269 家**（浙江 98 / 省外 171）——
两条都钉在测试里：赛道本身的**官方认定**档位不被调研数据顶掉，且
`?cluster=…&scope=zhejiang` / `scope=out_of_province` 能把它们拆开。

**顺带修掉的两个真 bug**（都是这一轮「整份挂一条赛道」的做法逼出来的）：

* **`also_in_other_lists` 是自报数**。`/api/admin/lists/import` 的报告把「这批企业与
  **其余**名单的关系」算成了「与骨架的关系」，而骨架里就有它自己 —— 于是 317 行
  100% 自报「已在别的名单里」（无缝那份也一直是 137/137）。现在按
  `source_key` 把本次要覆盖的名单从对照里摘掉再数。同时补了
  `dropped_from_db`：覆盖式导入会**取代**旧行而不是删除，所以「会少掉多少家」
  指的是「库里有、但这批不再收录、且不属于其它名单」的那部分。
  摘除只看 `source_key`，所以**修订版必须用同一个 `source_key` 覆盖**
  （这也是上面的导入命令为什么强调「用同一个 `source_key`」）；换一个新 key
  导入同一份文件，报告会如实说这批企业「已在别的名单里」—— 因为注册表里
  确实还留着旧 key 的那一份。
  这条规则现在有两处断言：`tests/test_tools.py` 直接量骨架与 `_database_delta`
  （离线，不需要令牌），`tests/test_api.py` 则用真 key 跑一次干跑看报告
  （干跑不写文件，顺手比对了注册表前后一致）。此前接口侧那条断言拿一个**新** key
  去要求「必须摘掉自己」，两个前提互相矛盾，所以只在带 `ADMIN_TOKEN` 时红 ——
  这也是「不带令牌的那条基线」一直看不见它的原因。
* **通用导入器不认「集群类型」列**（`核心区/协同区/新星产业群` + 赛道 → `415X-<赛道>`）。
  此前只有 `tools/parse_cluster_reps.py` 会算它，走接口导入时「集群代表企业」
  那批行会**全部挂不上它们代表的赛道集群**。现在两处同一语义：核心区/协同区
  在这里换算成 slug；「新星产业群」交给 seed 侧按「县市区 + 细分赛道」匹配
  （所以它不算「未识别」），其余认不出来的取值才进 `unknown_cluster_types` 警告。

**「市级归口」是本轮新增的行政区角色。** 9 个产区里 7 个的成员散在好几个县区

而不是「未标注产地」；桐庐内窥镜与东阳医疗器械是县级产区，照常挂到县。

**顺带修掉一个把浙江企业算成省外的 bug。** 镇街级清单那 18 家「对标龙头」里，
有 4 家的企业本身就在浙江（天堂伞在萧山、均胜在宁波、森马与人本在温州）——
清单写的是「非本地产区」（不是那个镇街产区的企业），早先的实现把这句读成了
「不在浙江」，于是 4 家浙江企业被划进「省外 273」，既不参与浙江统计，
企业页上还写着「省外产区」。现在省外与否只看**企业自己的地址**：

| 情形 | 处理 | 页面 |
| --- | --- | --- |
| 14 家地址在外省/境外 | `region_source = out_of_province` | 省外产区 · 仅作对比参照 |
| 4 家地址在浙江 | `region_source = benchmark`（新增） | 对标龙头 · 不是该产区的企业，不参与产区统计 |
| 18 家 | 都不参与**产区**统计，都保留清单标注 | —— |

结果是省外从 273 降到 269、浙江从 1980 涨到 1984，`省外 ∈ 浙江政区` 这条
自相矛盾的数据（天堂伞既有萧山区又被标省外）也一起消失了。

### 「全国代表企业」清单：给已有官方集群配企业，不新建集群

第四批产业集群的代表企业清单和前面两份**性质不同**：前两份各自带一个新产区，
这一份是**给已经建档的官方集群配代表企业**（每个集群 3-6 家）。所以它不新建集群，
而是往 `enterprise_cluster` 里加归属：

| 清单的「集群类型」 | 挂到哪个集群 |
| --- | --- |
| 核心区 / 协同区 | 对应的 `415X-<赛道>` 集群（那个集群的 `cluster_region` 里本来就记着哪些县是核心区/协同区） |
| 新星产业群 | 对应的 `newstar-NN-<细分赛道>` 集群，按「县市区 + 细分赛道」匹配 |

**顺带修掉一个我自己造出来的重复**：上一轮导入武义户外、义乌无缝时，我以为它们没有官方档案，
就各建了一个调研集群；其实现有库里已经有官方第四批的
`newstar-19-户外运动与休闲`（武义县）与 `newstar-18-无缝服装`（义乌市）——
**同一个产业群出现了两条档案**。现在把企业直接挂到官方集群上，
调研成果（17 条带口径的规模指标、行业荣誉）改成**叠加层**（`research_clusters.json` 的 `overlays`），
集群主体仍以官方名单为准。根因是 `seed_newstar_clusters()` 原先跑在 `seed_enterprises()` **之后**，
企业入库时那些集群还不存在，只能挂空——现在把集群层整体提到企业层之前。

另有两处字段判断值得记下来：

* **一家企业可能是多个集群的代表**（深圳市兆驰、西安铂力特在清单里各出现两次），
  所以归属是列表，主集群取第一个；和官方名单按赛道算出来的归属撞到同一个集群时**不重复挂**。
* **有 17 家企业同时出现在官方名单和这份清单里**，合并后仍按官方认定的地区与核实程度展示。

#### 修订版（副本）与批量导入接口

作者随后给了修订版 `docs/浙江第四批产业集群_全国代表企业清单_副本.csv`（387 行 =
第一批 161 + 第二批 226）。核对下来，**第一批的 161 行与原文件逐字段完全一致** ——
副本是原件的整体升级，不是另一份清单。所以走批量导入接口，用**同一个 `source_key`** 覆盖它：

```bash
curl -X POST $BASE/api/admin/lists/import -H "X-Admin-Token: $ADMIN_TOKEN" \
  -F file=@docs/浙江第四批产业集群_全国代表企业清单_副本.csv \
  -F list_name='浙江第四批产业集群全国代表企业清单（第三方调研）' \
  -F source_key=cluster_reps -F grade=site_curated \
  -F source_file=docs/浙江第四批产业集群_全国代表企业清单_副本.csv
```

导入 = 证据层 + 联系方式层 + 候选官网层三份产物，外加注册表条目。**同一 `source_key`
再导入就是覆盖**：清单里被作者删掉的企业会跟着消失，而不是留在库里。

这批新数据里有三个形态值得单独说，处理方式都写在 `services/list_import.py`：

| 形态 | 例子 | 处理 |
| --- | --- | --- |
| 没见过的「官网类型」 | `经销商站`（假设） | **不发布为官网** + 写进备注 + 报警告。默认当成企业官网等于替清单做判断 |
| `待核` + 裸域名 | `99hxy.com` | 不发布，但作为**候选**送进本站验收门（验过才算数）；来源自己都没把握，我们凭什么直接发布 |
| 哨兵值里夹带的线索 | `待补（杭钢集团 hzsteel.com）` | 只写进备注。那是集团的站，而验收门那条路径带不了「指向集团」的标注 |

同时新增两种链接类型标注：**母公司官网**与**品牌站 / 品牌海外站**（页面上分别显示
「指向所属集团/母公司站点」与「链接类型：品牌站」）。集团/母公司站点**收**（同一集团
多家子公司共用一个域名很常见），但必须带标注，否则读者会以为那是工厂自己的站。

### 镇街级块状经济清单：第一次把调研单位下沉到镇街

第五份清单《浙江省镇街级块状经济企业清单》（264 家 / 46 个产区）与前几份的关键差别：

| 差别 | 为什么重要 |
| --- | --- |
| **逐行自带归属**（地市 / 县市区 / 镇街 / 块状经济 四列） | 产地归属由清单决定，不靠我们按地址或产品去猜。46 个产区全部映射到已有集群，一行都没挂空 |
| **18 行是「对标龙头」** | 施耐德、立讯精密、恒力石化这些是拿来对标的外省/境外龙头，不是该产区的企业。它们标 `out_of_province` / `benchmark`，**且其地址不能代表产区位置**（施耐德在上海、立讯精密在东莞） |
| **产地列的两种含义** | 「对标龙头·非本地产区」是外省企业；「对标龙头·非南阳产区」是**浙江企业但不是这个镇街**（天堂伞业在杭州萧山）。混成一个数字就会得出「18 家省外」这种错误结论 |
| **有官网 ≠ 打得通电话** | 调研方明确未做回拨核验。浦江水晶 6 家里 5 家有官网、**0 家**公示座机；浙江大唐袜业集团官网公示号码直接打码。所以 `电话性质` 一列原样保留并显示在页面上（「电话性质：总机（官网）」） |

**「对标龙头」的处理**是这一份最需要小心的地方，具体做了三件事：

1. 记 `region_source = benchmark`，「不参与该**产区**的统计」；
2. **不采用它的行政列作为企业所在地** —— 那几列写的是「本地产区」的位置（宁波均胜挂在
   瑞安塘下产区名下，列值写的是「瑞安市」），照抄会把这家宁波公司标成温州企业。
   所在地只能从它**自己的地址与备注**认（认不出就留空，宁可不填）；
3. 把清单的原始标注写进备注（`清单标注：对标龙头·非本地产区`），页面上能看出是哪一种。

第 1 条**不等于「标省外」**：18 家里 14 家在省外/境外，4 家（天堂伞萧山、均胜宁波、
森马与人本温州）本身就在浙江 —— 省外与否按企业自己的地址判，不把它们划出浙江统计。
所以 `out_of_province`（省域）与 `benchmark`（产区关系）是两个正交的事实，
两个都真时记 `out_of_province`（行里优先看省域）。

**同样的产业带换了个名字出现**时，指向已有档案而不是新建：塘下汽摩配 → 瑞安汽摩配、崧厦伞业 → 上虞伞业、店口铜加工 → 店口五金、云和木玩 → 云和木制玩具。映射表在 `services/list_import.py` 的 `CLUSTER_SYNONYMS`，只列**确定是同一件事**的；拿不准就不加，让那一行没有集群归属再人工判断 —— 挂错集群比不挂更难发现。

### 临安区规上企业底表：与前面六份都不是一回事

第六份《临安区规上企业基本信息20260731.csv》（594 行）是一张**政府公开的企业底表**，
不是调研清单。它的字段构成决定了它只能干一件事：**证明主体存在、并确定产区归属**。

| 它有 | 它没有 |
| --- | --- |
| 企业名称、统一社会信用代码、成立日期、经营状态、所属街道、行业代码与名称、区级产业分组 | **官网、电话、地址、联系人** |

三条处理原则：

1. **它是「谁存在」的证据，不是「怎么联系」的来源。** 593 家企业入库后
   `with_phone` / `with_website` 都是 0 —— 这是如实的，不是导入失败。
   把一张没有电话的表导成「有联系方式」，比不导更糟。
2. **档位是「政府公开信息」，不是「官方认定」。** 规上企业是统计口径
   （年主营业务收入达标），不是产业政策认定；两者混用会让「官方认定」这个标签贬值。
   新增 `gov_open` 档后，名单级的档位合并也从「官方 vs 调研」改成**显式优先级**
   （`GRADE_RANK`：官方 > 政府公开 > 媒体 > 站方整理 > 自报）——
   以前写成 `if grade == "official"`，三档之后那样写就变成「取决于名单读取顺序」。
3. **产区归属从「所属街道 × 产业名称」的交叉表里读出来，不猜。** 13 个临安产区
   已在 `build_seed.py` 建档；原表 14 个分组里「装备制造」与「其中高端装备」

海运集装箱 54，**整列无空值**）。它就是这份清单的产品，所以进了

### 调研清单的行政列写的是「产区」的位置，不是企业的注册地

这条是上一条（「对标龙头」）的推广 —— 它踩过的坑不止出现在对标龙头那一行上。

《浙江省镇街级块状经济企业清单》与《浙江省产业带企业调研清单》逐行给出
「地市 / 县市区 / 镇街」四列。这四列**共同描述那个产区在哪**：清单是在说
「这家企业是我们为柳市低压电器产区找来的」，不是在说「这家企业的注册地在柳市」。
两个事实在绝大多数行上碰巧一致，所以按列值直接入库看不出问题；
一旦不一致，错的都是**看起来完全合理**的那种错：

| 企业 | 清单的列值（产区坐标） | 企业自己的所在地 |
| --- | --- | --- |
| 宁波均胜电子（瑞安汽摩配产区的对标龙头） | 宁波市 / **瑞安市** / 塘下镇 | 宁波市（地址写「宁波市国家高新区清逸路99号」） |
| 巴拉巴拉（浙江森马服饰） | 温州市 / **吴兴区** / 织里镇 | 温州市 |
| 中银（宁波）电池 | 宁波市 / **宁波高新区** | 宁波市江北区 |
| 舟山海洲水产 3 家 | **上海市** / 普陀区 / 沈家门街道 | 舟山市普陀区 |
| JUKI（日本重机）/ 新秀丽 / Herman Miller / 鄂尔多斯 | 台州市 / 嘉兴市 / 湖州市（**产区所在的市**） | 境外 / 内蒙古（地址列写的是产地标记） |

三类错误各有各的成因，修法也不同：

1. **列值互不自洽**（宁波市 + 瑞安市）—— 这些列指向的是同一个产区，而产区只有一个位置，
   所以「市 + 县」必须同属一条行政链。不同链就说明这些列值不可能是这家企业自己的，
   一行都不采信（地区由其余名单里已确认的值补上，或留空）。
   判断只能拿**浙江的**区划表做（`DISTRICTS`），外省的县不在表里。
2. **省级地名重名**（舟山的普陀区 vs 上海的普陀区）—— `looks_outside_zhejiang` 先认出
   「上海市」，于是地址里那个「普陀区沈家门街道」被判成外省，整行跟着记 `out_of_province`。
   判据改成两个事实分开看：**地址里认得出浙江的市**就按浙江算，
   列值写的外省市只在地址完全认不出浙江时才采信（那才是真的在外省）。
3. **地址列写的是产地标记而不是地址**（「日本」「境外」「内蒙古」「安徽」）——
   `PLACE_MARKERS` 认出这一格不是地址，于是这一行不能拿它认地区。
   同时「境外」两个字会撞上浙江地名（杭州的「上城 / 下城」里含「城」），
   所以判浙江地名前要先把标记从文本里删掉。

**「市 + 县」不自洽时为什么不按镇街列反查**：镇街列写的也是**产区**的镇街
（森马的「织里镇」在湖州，可这家企业在温州），照它反查会把「温州市」的企业
送进「湖州市吴兴区」—— 那正是第 1 类错误本身。所以镇街反查只在
「反查出来的市与地市列同市」时才用；两者不一致就是「这些列都在说产区」，直接留空。

**行政列给不出县、地址也给不出时**：厂址只写到市（「温州市永嘉工业园区」）就停在市级；
厂址是定位描述（「浙江湖州」）就按市级算；两者都没有但名录里别处有值就沿用别处的
（《浙江省产业带清单》对这几行的地址与列值都是空的，沿用不是「拿别人的地址」，
而是「不要把已经确认的地区清成空白」）。
逐行标「省外」的行不沿用 —— 那会把省外企业改成浙江企业。

改动落在 `services/list_import.py`（`geocode_row` / `benchmark_row` /
`looks_outside_zhejiang`）与 `seed/loader.py`（`DISTRICT_ALIASES` 补 4 个开发区）。
**存量数据要重导才生效**：产物文件里已经写死的地区不会自己改，
`tools/` 下那批 `parse_*.py` 走同一条 `import_list`，重跑即等价于重导。

### 名单批量导入：新增一份清单不需要改代码

```bash
POST /api/admin/lists/import      # multipart，需 X-Admin-Token
POST /api/admin/lists/reseed      # 按 data/ 清单重建数据层（= cli.reseed，账号与收藏保留）
GET  /api/admin/lists             # 已导入名单（注册表）
```

一次导入产生四样东西，下游全部自动认得：

| 产物 | 作用 |
| --- | --- |
| `data/source/<key>.json` | 证据层：逐行原样 + `raw` 子对象（哨兵值的原值就留在这里） |
| `data/curated/<key>_list.json` | 联系方式层：逐行带 `source_label`（A/B/C 档标签不同） |
| `data/curated/<key>_sites.json` | 候选官网层：**必须过验收门**才会以「站方核验 · 已比对官网」出现在页面上 |
| `data/curated/imported_lists.json` | 注册表：名单名 / 核实程度 / 行数 / 档位分布 / 原始文件 / 说明 |

骨架合并（`source_files()`）、联系方式分层（`load_contacts()`）、来源声明
（`/api/stats/sources`）、候选官网表（`seed_files()`）**都读注册表**，
所以新增一份名单不用在四个地方各改一次；注册表与内置名单按**文件名**去重，
核实程度以注册表为准。来源声明里的说明文字取自导入时填的 `used_for` ——
跟着数据走，而不是写死在代码里（写死了，名单一修订就变成假话）。
注册表里还有两个说明性字段，同样只在来源声明里出现：

| 字段 | 含义 | 例子 |
| --- | --- | --- |
| `role` | 这份名单在库里**承担什么**，显示在来源地图每行的名称旁 | 集群代表企业 / 产区企业层 / 赛道企业池 |
| `used_for` | 这份名单在库里**怎么用**（含本站对它的处理方式） | 「官网只作候选，须先核验」 |

两个字段都在导入时填，重新导入同一份清单时不填会沿用注册表里的旧值
（`role` 也是导入接口的可选表单字段）。**新导入的清单要记得填 `role`**，
否则来源地图那一行只剩一句说明长句，读者看不出它在库里干什么。

#### 覆盖是显式动作，不再由 source_key 隐式决定

「同一个 `source_key` 再导入 = 覆盖该名单」是后端的正确语义（修订版就该覆盖），
但**「没打算覆盖却覆盖了」是灾难**：名单页原先在打开时会把**最后一份**已导入名单的
`list_name` / `source_key` 预填进表单，于是「导一份新名单」静默变成「覆盖上一份」——
上一份的 264 行直接消失，首页数字几乎不变，而用户以为自己只是新增。

现在：

* 表单默认**全空**，`source_key` 不预填；
* 「导入方式」是一道显式选择：`新增一份名单` / `覆盖已有名单：<某份>（当前 N 行）`；
  选中覆盖时页面上会出现红字警告（写明会取代多少行、删掉的企业会跟着消失）；
* 即使绕过界面直接调接口，前端也会在 `source_key` 与已有名单撞车且未选覆盖时**拦住不发请求**
  （报错文案告诉用户该选覆盖还是换 key）。后端仍是「同名即覆盖」，这条只管「意图」。

#### 「赛道」列也能落位（415X 调研清单）

`resolve_cluster_slug` 原先只认 `list_cluster_slug` / 整份归属 / 产区列 / 集群类型列。
于是《浙江省415X先进制造业企业调研清单》（779 行、21 个赛道、**没有**集群类型与产区列）
会有 21 个赛道全部落空 —— 报告写着「可落位 0」，接口却回 200「成功」，
779 家企业进了库却不出现在任何集群页。

现在按两条**有据可依**的规则兜底，且都放在最后（行内集群列更具体，优先）：

1. 赛道名就是某个官方 415X 赛道 → `415X-<赛道>`；
2. 赛道名是某个官方「新星」产业群名，**且该企业所在县就是那个产业群的县** →
   `newstar-NN-<产业群>`。县名先归一（奉化市≈奉化区、天台县≈天台经济开发区）。

做不到就不落位（不按字形相近去猜）。实测 779 行里 669 行落位、110 行无集群可挂
（赛道只对应外地产业群，如滨江区的「光电（半导体）」——它不属于那 4 个县）。
报告与灌库**走同一个函数**，所以报告里的数字就是灌库后的结果；
报告按「行」计数并列出每个赛道落到了哪些产业群，不再是「整组取最后一行」。

#### 「产业带」列：别名漏了，而报告把这个漏洞做成了「正常结论」

《浙江省产业带企业调研清单》（594 行）用**「产业带」**这一列声明归属。
列名别名表里当时只有「块状经济 / 块状经济名称」，于是这一列**完全不被识别**
（`resolve_columns` 只认别名，认不出的列直接丢掉）—— 594 行全部没有集群归属。

更糟的是报告：`_cluster_mapping` 只统计「有集群类型/赛道列」的行，
于是这份清单得到 **「集群归属 0 / 0 行」**。那不是「全落位」、也不是「全落空」，
而是**什么都没算**，页面却把它渲染成一行正常结论。

三处一起改（缺一条都不算修好）：

1. 别名表加上 `"产业带"`（与「块状经济」同义：都是「这行属于哪条产业带」）；
2. `cluster_slug_index()` 补齐**灌库后才会存在的那批集群**：415X 赛道
   （`clusters_seed.json` 的 `tracks`）与 22 个「新星」产业群
   （键必须是 `{县市区}{产业群}`，与 `seed_newstar_clusters` 的命名一致；
   **不加裸名** —— 4 个县都有「光电（半导体）」，裸名只能指向其中一个）；
3. `_cluster_mapping` 改成**按行进总数**，并给出「按哪一列落位」（`bases`），
   每行必进某一个桶，不再出现「0 / 0 行」这种看着像结论的空算。

##### 顺带修掉一个归属错挂：区级产业分组表被无条件查询

`LINAN_INDUSTRY_CLUSTERS` 是**临安区规上企业底表**的区级产业分组表
（「集成电路」「新材料」「装备制造」这类很宽的名字）。它自己的注释写着
「分组的名字与档案的名字可能一致，但含义的来路不同，分开写才不会互相污染」，
而 `dispatch_cluster` 当时是**无条件**查它的 —— 正是注释里要避免的污染。

实测后果：产业带清单里「集成电路」指 415X 赛道（24 行，分布在萧山/北仑/富阳/
滨江/越城），却被这张表截走、全挂到 `linan-jichengdianlu`（临安集成电路）。
现在 `dispatch_cluster` 多收一个 `basis` 参数，**只有依据确实是「区级产业分组」时**
才查那张表；同一份清单里写「临安集成电路」的行仍正常落到临安那条档案。

归属依据的显示也改成了**实际列名**（「产业带」「块状经济」「产区」），
不再一律写「块状经济」—— 否则读者会以为我们认错了列，也就无从判断该不该信。

**干跑（`dry_run=true`）会回答四个问题**：这批数据长什么样（行数 / 企业数 / 档位分布 /
官网电话地址覆盖 / 省外数 / 批次）、多少行挂不上已有集群、相对现有库新增多少家、
以及被拒绝的行都是什么原因（手机号 / 残号 / 未识别的官网类型 / 第三方商铺链接）。
**挂不上集群的行会静默地不出现在任何集群页上**，所以它单独列出来。

页面入口：`/admin/contacts` 底部的「批量导入名单 CSV」（同一个接口，带干跑预览与报告）。
页脚的「数据导入」（在「关于本站」与「数据来源与核实程度」之间）用 `#import` 直接落到这一段。

**接口不碰数据库** —— 产物文件才是数据源。**导入成功后前端会自动接着灌库**
（`POST /api/admin/lists/reseed`），所以「导完首页数字没变」不会再有；
同一段里仍保留「按 data/ 清单重新灌库」按钮，给手工补充联系方式、修改产业带档案后用。
终端等价命令是 `cd backend && ../.venv/bin/python -m app.cli seed --drop`。
三者调用的是 `app.cli.reseed()` 同一个函数，只重建数据层（地区 / 集群 / 企业），
**账号与收藏保留**。

### 命令行也能直接导 CSV：`seed --csv`

`seed` 原先**只能**从 `data/source/*.json` 灌库。一份新 CSV 放进 `docs/` 之后，
不经过网页端、也没配一个 `tools/parse_*.py`，它就永远是磁盘上的一个文件 ——
`seed --drop` 对它毫无反应，而输出里一个字都不提。照着文档跑完发现「新名单里的
公司一家都没进库」，看起来就像命令坏了。现在 `seed` 直接吃 CSV：

```bash
# 已登记过的名单：只给文件就够，元数据从注册表读
cd backend && ../.venv/bin/python -m app.cli seed --drop \
    --csv docs/全国集装箱移动房企业调研清单.csv

# 从没导过的 CSV：给它一个 source_key 与名单全名
cd backend && ../.venv/bin/python -m app.cli seed --drop \
    --csv docs/某某清单.csv --source-key my_list --list-name "某某清单（第三方调研）"

# 只解析、只看报告，不写产物也不灌库
cd backend && ../.venv/bin/python -m app.cli seed --dry-run --csv docs/某某清单.csv \
    --source-key my_list --list-name "某某清单（第三方调研）"
```

四个刻意的设计：

| 决定 | 为什么 |
| --- | --- |
| **路径可相对仓库根**（`docs/x.csv`） | 文档里那条命令在 `backend/` 下执行，而人们在 README 里抄的路径都是相对仓库根的。绝对路径 / 相对当前目录 / 相对仓库根三种都认 |
| **已登记的名单不必再给元数据** | 按**文件名**匹配注册表就沿用 `source_key / list_name / grade / used_for / role`。再抄一遍的话，抄错一个字就是另一个 `source_key` —— 同一份名单在库里成两条，企业被拆到两边 |
| **未登记又没给 `source_key` 时直接停下** | 这个键是产物文件名 + 注册表唯一键 + 「再导一次是覆盖还是新增」的判据，不能猜。报错里给出可直接复制的命令 |
| **多份 `--csv` 配一条元数据会被拦住** | 一条 `--source-key` 套到 N 份文件上会把它们全写进同一条注册表记录（后一份覆盖前一份） |

**报告里最要紧的是「集群落位」那一段**，不是行数：

```
  集群落位    1069 / 1069 行（产业带）
```

认不出来的「产业带 / 块状经济」取值不会报错、也不挡导入，那些企业只是不进任何
集群页 —— 这个库因此先后丢过 355 行和 1069 行。所以 `--csv` 的报告会把未落位的
取值**逐个列出来带行数**，并指向建档脚本。`tests/test_tools.py` 里那条
「每份名单的取值都有对应档案」是它的守门员（白名单只有两条刻意的跨产区企业池）。

`--csv` 与网页端导入调用的是**同一个** `import_list()`，产物与注册表完全一致；
`cluster_mapping()` 也已经是服务层的公共函数（原先藏在 `routers/admin_lists.py` 里，
命令行要用就得从路由里 import，那是反向依赖）。

**为什么导入成功后自动灌库、而不是留给用户再点一次**：导入只写 `data/` 下的产物文件，
数据库一行不动；不灌库，首页「已收录企业」永远不会变。此前把这一步交给用户，
实际结果是「导完了没反应」，还被当成 bug 报回来两次。
状态提示写在导入按钮旁边（`已生效（用时 N 秒）：…企业 2704`），
不再只写在本页最顶部——那一段在浏览器可视区之外，等于没提示。
干跑仍然只解析、不写盘、不灌库。

**自动灌库之后，还有第三个「看起来像 bug 但不是」的情况**：导入一份**里面的企业
全部已在库**的名单（《浙江省产业带企业调研清单》就是 —— 594 家一个不新增），
灌库前后数字当然完全一样。接口一直算得出这件事（`database.new_to_db` /
`also_in_other_lists`），但屏幕上只写「已导入 594 行」，于是被第三次报成 bug。
现在导入成功的提示和报告里都写明「新增 N 家（这 594 家已在其它名单里，收录总数不会变）」。
**判据是数据，不是页面行为**：「数字没变」只有在 `new_to_db` 也等于 0 时才成立。

### 企业档案字段（成立年份 / 注册资本 / 核实档位）

这三项随清单一起进库，展示在详情页的「企业档案（来自名单原文）」：

* `registered_capital` 按**原文**存字符串（「100万元」写法不一，折算成数字会引入我们没能力核实的口径判断）；
* `verify_tier` 是**该企业在来源名单内**被核到什么程度，和名单级的 `data_grade` 是两件事，分开存；
* 三者都可以在人工补充 CSV 里填（见「人工补充」），填了以人工层为准，并且只由人工层提供来源标注
  —— 自动发现层的记录本来就带着名单里的原值，若允许「任意层都可提供」，名单里抄来的年份
  会被标成「站方核验 · 已比对官网」，等于给一个从没抓过的字段盖「已校验」的章。

**联系方式覆盖率的诚实说明**（实时数字看 `/api/stats`）：

官网发现走「候选生成 + 强验收」，覆盖率受两个因素限制：

1. **验收规则很严** —— 宁可留空，也不猜一个网站挂上去（错收会毁掉「官方认定」标签的可信度）；
2. **候选来源的可得性** —— 不少中小工厂**本来就没有官网**，或站点只有英文/无企业全称，
   按规则一律不收录（例如「先临三维」的官网是纯英文，无法证明是该企业，因此留在待人工补充清单）。

**覆盖率主要靠调研清单，不靠爬搜索引擎。** 三份调研清单直接带来数百条官网与电话，
是当前最主要的来源；搜索跑批**已不再是必需步骤**（见「官网发现」一节的说明）。
未通过验收的一律留空，由人工补充兜底。**这不是数据缺失，是没有把握时不做判断。**

### 「官网」字段：链接指向什么，必须标出来

调研清单会带一列「官网类型」。这一列不能丢：

| 官网类型 | 处理 |
| --- | --- |
| 企业官网 / 科研机构官网 | 进 `website` |
| **集团官网 / 母站企业官网** | 进 `website`，但页面标注「指向所属集团/母公司站点，不是本企业独立官网」 |
| **第三方商铺 / 第三方·集团站** | **不进 `website`**，链接写进备注备查 |

第三方商铺页填进官网字段的后果很具体：采购商点进去看到的是一个中间平台的页面，
而不是工厂本身（调研文档专门警告过这一点）。集团官网则是同一个集团下多家子公司
共用同一个域名（例如三家安费诺子公司都指向 `amphenol.com`），不标注就会让人以为
这三家是同一个站。

### 联系方式来源分层（同一页面上按字段分别标注）

一个页面上的「电话」可能来自四个可信度不同的地方，所以来源是**逐字段**记录的，
而不是给企业打一个总标签：

| 优先级 | 层 | 页面标签 | 含义 |
| --- | --- | --- | --- |
| 1 | `manual_sites.json` | 人工补充 · 站方核对 | 维护者手工填写，可信度最高 |
| 2 | `discovered.json` | 站方核验 · 已比对官网 | 企业自己的站点已核验通过（域名与主体对得上），再从该站点读取联系方式 |
| 3 | `enriched.json` | 站方整理 · 已比对官网 | 早期候选清单的核验结果（兼容保留） |
| 4 | `directory_contacts.json` | **搜索结果摘要 · 原站未核验** | **没有访问过企业自己的站**，只从搜索结果摘要文本里读到电话/地址（**该层已暂缓扩展**，见「搜索跑批已不再是必需步骤」） |

第 4 层是第三阶段尝试过的兜底：大量中小工厂确实没有可核实的官网，但搜索摘要里往往
已经有聚合站给出的总机和地址。取用它的同时必须守住三件事：

* **标签降级**——不能和「站方核验 · 已比对官网」共用样式，页面上一眼能看出没核验过原站；
* **免费**——只读 `tools/search_discover.py` 已经抓下来的摘要缓存，**不发任何搜索请求**，
  所以改抽取规则可以反复重跑（`tools/directory_contacts.py`）；
* **三道闸**——摘要必须提到该企业；号码走同一套严格校验器（手机号一律不采）；
  **跨企业重复出现的号码丢弃**（一个号码横跨多家企业，几乎一定是聚合站的客服电话）；
  另外非浙江区号且非 400/800 的号码不予采信。

## 官网发现：候选 + 强验收，而不是直接信任搜索结果

原始 HTTP 访问搜索引擎在本环境一律被拦（Bing 返 bot-challenge、Baidu/so.com 不稳、
DuckDuckGo/Mojeek/Brave/Ecosia/Yandex 403 或验证码、ICP 备案接口 JS 化或需付费 key）。
**但驱动真实浏览器可以**——实测 360 / Sogou / Baidu 的结果页都能正常加载。
因此分两条候选来源，最终都过**同一道验收门**：

```
① 浏览器搜索（tools/search_discover.py）         ② 确定性候选（tools/discover_sites.py）
   "<企业名> 官网" → 结果域名                       站方清单 / 品牌域名表 / 拼音变体
        └──────────────┬──────────────────────────────┘
                       ▼
             DNS 预筛（只对能解析的域名发 HTTP）
                       ▼
             强验收（规则 v4）—— 页面必须出现企业全称
                       ▼
             联系方式抽取（剥 script + 手机号拒绝 + UUID 片段拒绝）
```

**搜索结果只是候选，不是结论**：命中的域名照样要过验收门，
所以引入搜索并没有降低精度。这里的取舍是刻意的——
一个标着「官方认定」的目录，**错误归属的代价远大于漏收**。

### 真正的瓶颈是限流，不是代码

实测：**约 270 次自动搜索后，360 / Baidu / Sogou 会同时开始返回空页或验证页**
（`访问异常页面`、`百度安全验证`）。因此 `tools/search_discover.py`：

* 默认**刻意放慢**（`--delay 10 --jitter 8`，约 3-4 家/分钟）；
* 连续若干次搜不到结果时**自动暂停退避**（`--empty-streak-limit` / `--cooldown`，默认 30 分钟）；
* **空结果不写缓存**——分不清「真没结果」还是「被限流」，就宁可下次重查，
  绝不把限流污染固化成结论；
* 把结果缓存到 `data/cache/search360/`，可随时中断续跑：已在本版规则下查实为否定的企业会被跳过，
  续跑不再重走几百家（改过验收规则之后它们会被重新走一遍，这是必须的）。

> 正确做法是**放慢**，不是伪装绕过（换 UA / 代理）——前者是尊重对方服务，后者是规避访问控制。

### 搜索跑批已不再是必需步骤

上面这一节记录的是「如果非要用搜索引擎该怎么做」。**当前不再依赖它**：

* 覆盖率由三份调研清单提供（官网/电话/地址直接给出，不需要猜域名）；
* 调研清单给的官网仍然要过同一道验收门，所以精度没有放松；
* 后台不再常驻搜索任务。`tools/search_discover.py`（浏览器搜索）与
  `tools/directory_contacts.py`（只读搜索摘要的兜底层）保留但**已暂缓**，不进标准管线。

真要恢复大规模搜索，正确做法是采购**合规的商业搜索 API**（可批量、稳定、不受验证码影响），
而不是靠拉长跑批时间——限流是对方的访问控制，放慢是尊重，绕过不是。

### 验收规则的四次迭代（每次都由真实误报或漏报驱动）
| 版本 | 规则 | 被它放进来的真实误报 / 漏报 |
| --- | --- | --- |
| v1 | 企业**简称**出现在 `<title>` | `中南仪表有限公司` 命中 `南阳市中南仪表有限责任公司`（外省无关企业） |
| v2 | 企业**全称**出现在页面任意位置 | `杭州信多达智能科技有限公司` 命中信多达**电器**的站点（全称只出现在地址行里 1 次） |
| v3 | 全称在 `<title>`，**或**在版权/备案标记（`版权`/`Copyright`/`©`/`ICP备`/`主办单位`）后 90 字符内 | —— 但**漏掉了大量真站**（见下） |
| **v4（当前）** | 前两条，**或**「全称在**正文中处于自我介绍句式**（`…有限公司是一家专业从事…`），且标题没有声明另一家公司」 | —— |

**v4 修的是漏报，不是误报**。v3 要求全称必须落在标题或版权行里，但真实企业站
常用「标题只挂品牌、版权行只挂品牌、全称只在公司简介里」的写法，于是被判为查不到：

* `杭州惠耳听力技术设备有限公司` —— 官网 `huier.org` 标题是「助听器品牌…--惠耳听力」，
  版权行是「Copyright © … 惠耳听力 版权所有 浙ICP备08000334号-1」，
  全称只出现在简介第一句「**杭州惠耳听力技术设备有限公司是一家专业从事**助听器研发…」。
* `巨人通力电梯有限公司` —— 官网 `giantkone.com` 同理（标题仅「巨人通力-首页」）。

新增的 `body-selfid` 路径要求全称**紧接**自我介绍句式（是/系/成立/拥有/位于/专业从事/以下简称…），
这样「全称出现在地址行」的提及形式仍然不算数：

* `杭州信多达智能科技有限公司` 仍被拒 —— `xinduoda.com` 上是
  「地址：杭州市大江东产业聚集区经六路2977号，**杭州信多达智能科技有限公司** 联系电话：…」，
  全称后面跟的是「联系电话」而不是句式词；该站标题也声明了另一家主体（`杭州信多达电器有限公司`），
  被「标题里的其他公司主体」这道闸再次挡住。
* `华峰化学股份有限公司` 仍被拒 —— 母公司「华峰集团」站从未以自我介绍句式提到子公司。

**缓存语义随之收紧**：v3 时代允许「复用旧版本的否定结论」，理由是「规则只会越改越严」。
v4 是**放宽**的，而 huier.org / giantkone.com 恰恰躺在旧的否定缓存里，
所以跨版本复用否定的逻辑改为白名单 `NEGATIVE_REUSE_VERSIONS`（v4 下为空集）——
以后再次放宽规则的人必须重新评估，而不是默认复用。

「标题只有品牌名」的真站（海康机器人、晶盛机电、浙江中煤机械）之所以一直能保住，
是因为它们的**全称出现在版权行里**（`copyright` 路径）。

搜索路径还**修正**了一个拼音路径的错误：`中南仪表有限公司` 此前被误配到南阳那家，
改用搜索后命中 `znmeter.com`（标题即「中南仪表有限公司-电能计量产品生产商」，与浙江这家吻合）。

**精度审计**：所有已核实记录都会跑一次 `--revalidate`，逐条重放当前规则。
近一次结果：**95 条通过、0 条被判误收**（另有 1 条因站点临时返回 204 无法判定）。

**「抓不到」不算「不通过」**：复验时若站点超时 / 204 / 连不上，记录只标 `recheck_needed`，
**保留原结论不降级**——否则一次网络抖动就会静默删掉好数据，而这正是最难被发现的数据损坏。

**性能**：候选校验改为并发（`verify_first`，6 并发）。这些请求打的是**候选企业自己的站**，
不是搜索引擎，所以并发不影响限流，只压缩本地等待——全量跑批从「按候选数×超时串行累加」
变成「一轮超时」。

## 人工补充（自动发现兜底）

自动发现核实不到的企业，通过三层机制补全，优先级最高且页面明确标为「人工补充 · 站方核对」：

| 方式 | 适用 | 命令 / 入口 |
| --- | --- | --- |
| CSV 往返 | 批量整理（Excel / Numbers） | `python tools/manual_csv.py export` → 填写 → `python tools/manual_csv.py import` |
| 管理 API | 集成到其他系统 | `POST /api/admin/contacts`、`POST /api/admin/contacts/bulk` |
| 网页表单 | 逐条边看边填 | `/admin/contacts`（需 `ADMIN_TOKEN`） |
| 撤回 | 填错了要回退 | `DELETE /api/admin/contacts?name=<企业名>`，或管理页「已人工补充」里的「撤回」 |

三种方式共用**同一份校验实现**（`backend/app/services/contacts.py`），写入同一个文件
`data/curated/manual_sites.json`，因此规则不会漂移。

**必须能撤回**：人工补充的优先级最高，**填错就会盖住自动发现的结果**；
在此之前管理界面只能新增、不能撤销，填错一条就只能手工编辑 JSON。
一个「优先级最高」的层没有撤销入口是迟早会被用到的缺口。

**企业名走查询参数而不是路径参数**：真实数据里有「Herman Miller / Steelcase」
这种含斜杠的名字，编码成 `%2F` 之后仍会被先解码再切分路径，`DELETE` 会落到 404 上。
企业名是**数据**，不是标识符。

校验会拒绝：

* 不在名单中的企业名（名单 = 官方名单 + 已导入的第三方调研清单，避免产生无依据的记录）
* 任何个人手机号（本站不采集个人联系方式）
* 非 `http(s)` 的官网、非法邮箱
* 成立年份不是 1949-2100 的四位年份

CSV 的 `current_*` 列只作参考、不会被回写——否则会把自动发现的结果错标成人工补充。

### CSV 列（含本次新增字段）

```
name, list_names, city, district,            # 身份与地区
verify_tier, products,                       # 只读：来源名单里的核实档位与主营产品
current_founded_year, current_registered_capital,
current_website, current_phone, current_email, current_source,   # 只读：现有结果，供参考
website, public_phone, public_email, address, source_url, note,  # 可填：联系方式
founded_year, registered_capital,             # 可填：企业属性（本次新增）
```

`verify_tier` / `products` / `current_*` 一律只读，原因是同一个：防止把「已有的结果」
在往返一次之后变成「这次人工补充的」，那样来源标签就失真了。

填完后重新灌库即可生效：`cd backend && ../.venv/bin/python -m app.cli seed`

## 启停：`./zanzhu.sh`

日常只需要这一个命令。它管的是**数据库 → 后端 → 前端**三件事的启动顺序与就绪确认。

```bash
./zanzhu.sh start              # 启（已在跑的自动跳过，逐个等到就绪）
./zanzhu.sh stop               # 停后端与前端（数据库保持运行）
./zanzhu.sh restart            # 重启
./zanzhu.sh status             # 看状态（端口 / 就绪 / PID）
./zanzhu.sh logs api 100       # 看日志（默认后端 40 行）；logs -f 跟随
```

可覆盖：`API_PORT` / `WEB_PORT` / `API_HOST` / `WEB_HOST` /
`PG_PORT` / `PG_DATA` / `PG_CTL` / `AUTH_SECRET` / `WAIT_SECONDS`。

### 三条设计原则（都是踩出来的）

1. **「在不在跑」只看端口，不只看 PID 文件。** PID 会被系统回收，陈旧的 PID 文件配上
   一个恰好复用了该 PID 的无关进程，就是「脚本说在跑、实际端口连不上」。
   端口是唯一判据，PID 文件只用来定位我们自己起的进程。
2. **就绪判据要看服务**吐出来的内容**，不能只看状态码。** 本机 8020 上常年跑着另一个
   Python 服务，`python -m http.server` 也回 200 —— 只看状态码会把它们当成我们的服务，
   报「全部就绪」，点开却是别人的页面。所以后端要健康检查里带站点名、前端要页面里带站点名。
3. **只停自己起的。** 端口被别的项目占用时，脚本报错并说清是谁，**绝不** kill 一个不认识的
   进程。判据是「命令行看起来是本库的服务」**且**「工作目录在仓库里」——
   只看工作目录会把「从本目录起的任何东西」都当成自己人。

### 一个 macOS 上的坑：没有 `setsid`

第一版想让服务自成进程组，停止时一个信号收掉整组。但 macOS 没有 `setsid`，
而非交互 shell 的子进程与脚本**同组** —— 发整组信号会把脚本自己一起打死。
所以改成逐个收集子孙进程（`pgrep -P` 递归）配合「谁占着端口」来收：
`uvicorn --reload` 的 reloader 与 worker、vite 的 esbuild 都是独立的子孙进程，
只 kill 父进程会留下占着端口的孤儿，下次启动报「地址已占用」，
而 `ps` 里那个进程的名字看起来完全正常。

### 脚本与数据库的分工

**启停脚本管的那份集群 ≠ 后端连的库。** 后端连哪个库只由 `backend/.env` 的
`DATABASE_URL` 决定；脚本的 `PG_PORT` / `PG_DATA` 说的是「脚本能替你启动的那一份」。

这两件事混在一起会出两种错，都能把人带到沟里：

* 把「5433 在跑」当成「数据库就绪」，而后端其实连 5432 —— 启动照报「全部就绪」，
  打开页面却没有数据（或数据是另一份）；
* 后端连的是外部库（Postgres.app / 容器 / 远端），脚本却去起一份本地集群 ——
  起完还占着一个没人用的端口，下次真要用 5433 就跑不动。

所以 `start` / `status` 会先解析 `DATABASE_URL`，按它的 host:port 判断可达性：

| `DATABASE_URL` 指向 | 脚本的行为 |
| --- | --- |
| 本脚本那份集群（`127.0.0.1:5433`） | 不在跑就 `pg_ctl start` 起它 |
| 别的 host/port（如 Postgres.app 的 `5432`） | **只探测可达性**，不启动、不占用；连不上就报错并说明它不由脚本管理 |
| `.env` 里没有 `DATABASE_URL` | 明确报「无法确认」，提示脚本只保证自己那份在跑 |

口令只经环境变量传给 `psql`（不进命令行）—— 同机其他用户能从 `ps` 里读到命令行参数。

### 数据库为什么不在 `stop` 里

`stop` 只停后端与前端，**数据库保持运行**：数据目录里是唯一一份数据，
停它只会在下次启动时多等几十秒，没有别的好处。需要停库时直接用
`pg_ctl -D ~/.local/share/zanzhu-pg stop`。

### 跨重启的登录态

脚本在没设置 `AUTH_SECRET` 时显式给一个固定值 ——
令牌签名密钥一变，**所有已登录的会话立刻作废**，用户会以为「重启把登录弄坏了」。
所以 `restart` 之后原来拿到的令牌仍然有效（已用 `/api/account/me` 验证 200）。

运行产物都在 `.run/`（`api.pid` / `web.pid` / 日志），该目录已在 `.gitignore` 里。

## 快速开始

### 1. 数据库

后端连哪个库**只由** `backend/.env` 的 `DATABASE_URL` 决定，与启停脚本的 `PG_PORT` 无关
（两者的关系见「脚本与数据库的分工」）。生产请用你自己的 PostgreSQL。

本库当前用的是 Postgres.app 那一套（端口 `5432`）。也可以用独立集群（端口 `5433`，
trust 认证，启停脚本能替你启动它）：

```bash
# 示例：独立数据目录 + 5433 端口（这样 ./zanzhu.sh start 会顺手把它起来）
initdb -D ~/.local/share/zanzhu-pg -U zanzhu --auth=trust --encoding=UTF8 --locale=C
pg_ctl -D ~/.local/share/zanzhu-pg -o "-p 5433" start
createdb -h 127.0.0.1 -p 5433 -U zanzhu zanzhu
```

`.env` 见 [backend/.env.example](backend/.env.example)：

```
DATABASE_URL=postgresql+psycopg://huangyong@127.0.0.1:5432/zanzhu
CORS_ORIGINS=http://localhost:5173,http://127.0.0.1:5173
SITE_NAME=浙江产业带企业库
ADMIN_TOKEN=            # 留空则不启用 /api/admin/**
```

**管理令牌的读取顺序：环境变量优先，其次 `.env`。** 两者都可以，但环境变量一旦传了
就会覆盖 `.env` 里的值 —— 顺序反过来会把运维临时指定的令牌顶掉。

> 踩过的坑：`ADMIN_TOKEN` 最初只从 `os.environ` 读，而 pydantic-settings
> **不会**把 `.env` 里的值写回环境变量（它只处理自己声明过的字段）。
> 于是「把令牌写进 `.env`」完全不生效，接口一直 404，看起来像功能没启用。
> 现在 `admin_token` 已声明为 Settings 字段，`tests/test_api.py` 也有一条断言专门守它。

## 产业带档案编辑（管理界面 / 接口）

集群页上的文字与数字有三类来源，优先级从低到高：

```
官方名单  →  第三方调研叠加层（research_clusters.json）  →  站方编辑（cluster_edits.json）
```

前两类随代码走，第三类在管理界面维护 —— 47 个镇街级块状经济**只有本站有**，
以前要改一句简介就得手工动 JSON 再整库重灌。

| 接口 | 作用 |
| --- | --- |
| `GET /api/admin/clusters` | 全部集群 + 是否已被编辑（含指标/荣誉数量、当前档位） |
| `GET /api/admin/clusters/{slug}` | 当前**生效**的值，供表单预填（不是叠加文件里的原始值） |
| `PATCH /api/admin/clusters/{slug}` | 字段级更新（只改提交上来的字段） |
| `DELETE /api/admin/clusters/{slug}` | 撤销编辑，回退到名单/调研叠加的值 |

页面入口：`/admin/clusters`。

**不可编辑的字段**：集群名称、档次、地理归属，以及**集群整体的核实程度**。
那些来自官方名单，改了就等于伪造认定依据；要改就得先改名单。
接口对未知字段直接 422（`extra="forbid"`），不会「收了但不用」。

**三条硬校验**（任何一条不合法都整体拒绝，不做部分写入）：

* 规模指标必须带 **口径 + 年份 + 来源** —— 前端在没有带口径的数据时不显示规模值，
  接口这一层也必须拒绝裸数字，否则那条规则只是句口号；
* 荣誉必须写 **授予主体**（没有授予方的称号无法核实，页面也就无法标档）；
* 核实程度只能是既定五档。

**简介的档位与集群的档位是两件事。** `cluster.data_grade` 说「这个集群的档案来自哪份名单」，
`cluster.summary_grade` 说「这段简介是谁写的」。给官方集群补一段站方简介，
不该把集群降级，也不该让一段没人签名的文字读起来像官方表述 —— 所以集群页上
简介旁边单独标出它的档位（例如「产区简介的来源档位：站方整理」）。

保存后需要重新灌库。终端：`cd backend && ../.venv/bin/python -m app.cli seed --drop`；
或页面上点「按 data/ 清单重新灌库」（`POST /api/admin/lists/reseed`）。
**重灌只重建数据层**（地区/集群/企业/关系表），账号与收藏保留。

## 用户与收藏

注册**无需邮箱或短信验证**（按需求）。把安全性放在别处：

* 用户名唯一 + 格式强校验（3-24 位字母/数字/下划线/汉字）
* 密码最少 8 位，且不能是纯数字、不能与用户名相同、不在常见弱口令表里
* 密码 **PBKDF2-SHA256 加盐哈希**（200k 轮）落库，绝不存明文
* 会话用 **HMAC-SHA256 签名令牌**（含过期时间，默认 30 天），服务端不建会话表
* 登录失败也会做一次哈希计算，避免通过响应时间探测账号是否存在
* 收藏是用户私有数据：需要登录、只能读写自己的记录（已覆盖跨用户越权测试）

| 接口 | 说明 |
| --- | --- |
| `POST /api/account/register` | 注册并直接返回令牌 |
| `POST /api/account/login` | 登录 |
| `GET /api/account/me` | 当前用户 |
| `GET/POST/PATCH/DELETE /api/account/favorites…` | 收藏列表 / 添加 / 改备注 / 取消 |
| `GET /api/account/favorites/ids` | 仅 id 列表，供列表页批量标记「已收藏」 |

| `DELETE /api/account/favorites/unresolved` | 清理「企业已不在名单里」的失效收藏 |

前端：`/login`（登录/注册同页）、`/favorites`（收藏 + 私有备注）。
企业卡片与详情页都有「☆ 收藏」按钮，点击**不会**跳转详情页。

### 账号与收藏必须活过「重新灌库」

数据更新 = 重新灌库。灌库**只重建数据层**（地区/集群/企业/关系表），
`app_user` 与 `favorite` 不在删除清单里 —— 否则每次更新名单都等于让所有人重新注册、
收藏清零。（曾经就是这样：注册后重灌一次，账号直接登录不了，看起来像「登录系统坏了」。）

**收藏按企业名称关联，不按自增 id。** 重灌会重建企业行，自增 id 随之变化：
今天 id 1006 是融鼎岳，重灌一次可能就变成另一家企业 —— 按 id 存的收藏会**悄悄改指向**，
用户看到自己从没收藏过的工厂。企业名称在本库唯一（`uq_enterprise_name`）且稳定，
就是要展示给人看的那个字符串，所以拿它做关联。因此 `favorite` 表**故意不加**
指向 `enterprise` 的外键：有了外键，重建企业表就得先删收藏，又绕回同一个问题。

代价与对策：名单若删掉某家企业，那条收藏会**失效**。失效收藏不会被静默丢掉 ——
`/api/account/favorites` 单独返回 `stale` 列表，`me` 里给出 `stale_count`，
`favorite_count` 只算能对上企业的那些（不能出现「说有 5 家只列 3 家」），
并提供一次性清理入口。

### 会话恢复：只有令牌真的无效才登出

`restore()` 先用令牌换用户、再拉收藏 id。两处都做了区分：

* 只有 **401/403** 才清除本地令牌（并让登录页显示「登录已过期」）；
  一次 500 或断网不会把人踢下线 —— 否则用户会以为是「登录系统坏了」，其实什么都没错；
* 收藏 id 拉取失败**不影响登录态**（列表页会再拉一次）。

任何带令牌的请求收到 401，都会通过 `onUnauthorized` 回调把本地登录态收掉，
页面不会一直显示「已登录」却点什么都报错。

### 登录 / 注册页面的三条约定

1. **不展示加密算法**。页面只说用户能判断的事（「密码不会以明文保存」），
   不写 `PBKDF2` / `SHA-256` / `HMAC` 这类实现细节 —— 它既帮不上用户，
   又等于把一个运维细节印在页面上。`/about` 的「账号与隐私」同一条口径
   （那段文字来自 `/api/stats/sources` 的 `account` 数组，改文案要改后端）。
2. **注册不采集联系方式**。原先有一个选填的「邮箱或电话，便于我们联系你」，
   与本站「不采集个人联系方式」「只公开一个联系邮箱」「不主动联系」的对外承诺冲突，
   已移除。数据库列保留（老数据不动），但界面不再索要。
3. **`redirect` 只接受站内路径**。登录后的跳转目标来自 URL，
   直接把外部字符串交给 `router.replace` 就是开放重定向；
   现在 `/` 开头、非 `//`、且不是 `/login` 才采信。

另有两处与登录直接相关的修复：

* `login()` 拉收藏 id 失败不再抛错。以前收藏接口抖一下，用户明明已经登录成功
  （令牌已写入），却被弹「网络请求失败」并停在登录页 —— 与 `restore()` 的处理对齐。
* 登录/注册成功后清掉 `session.expired`，否则重新登录成功、再进 `/login`
  仍会看到「登录已过期」的红字。

### 登录失败限流

`POST /api/account/login` 按 (用户名, 来源 IP) 记 15 分钟窗口内的失败次数，
超过 8 次返回 429。「无需验证即可注册」是需求，但它不等于「密码可以无限猜」。
计数放在进程内存里：单实例够用，多实例时应当在网关层做 —— 不为它引入一张
会被重灌清空的表。

**配置**：生产环境必须设置 `AUTH_SECRET`（令牌签名密钥）；未设置时会用内置开发密钥并告警。

```
AUTH_SECRET=your-long-random-secret uvicorn app.main:app
```

数据流（**谁被收录只看 source，联系方式才看 curated**）：

```
docs/*.pdf ──parse──▶ data/source/*.json ──────────────────────────┐
docs/*.csv ──POST /api/admin/lists/import──▶（同一条路径）          │
   ＋ curated/<key>_list.json（联系方式层）                        │

sites_seed.json ＋ 品牌域名表 ＋ 拼音变体 ＋ <key>_sites.json ──▶ discover_sites.py ──▶ curated/discovered.json
```

## 界面设计：档案台账

整套界面按 **frontend-design** skill 的两遍法做（先出设计计划、再对照简报自查、最后写代码）。
主体是**企业登记册**，不是创业公司落地页，所以视觉语汇取自中文官方文件与工商登记的排版惯例，
而不是「大数字 + 卡片墙 + 渐变」的默认款。令牌集中在 `frontend/src/styles.css` 的 `:root`。

### 四个决定

**① 字体：宋体标题 + 黑体正文。** 页面级标题用宋体（`Songti SC / Noto Serif CJK SC / STSong`），
正文用黑体栈。**不引外部字体** —— 本站已备案、面向国内访问，外部字体 CDN 既慢又是新依赖，
用系统栈的 fallback 兜住即可。数字统一 `tabular-nums`，这个库到处是计数与号码，对齐了才扫得动。

**② 档位钤记是唯一的强符号。** 五档核实程度此前只是五种颜色的同款药丸，去色或色觉差异下就失效，
且不带任何结构信息。现在档位由**形制**决定，色相只作辅助：

| 档位 | 形制 | 含义 |
| --- | --- | --- |
| 官方认定 | 实心深底 | 最强认定 |
| 政府公开 | 实心浅底 | 次强，权威但非认定 |
| 媒体 · 协会 | 实线边、无底 | 转述 |
| 站方整理 | **虚线**边 | 站方自己整理的，不是外部认定 |
| 企业自报 | **点线**边 | 最弱，已声明未核验 |

**③ 登记册取代卡片墙。** 企业名录与集群列表改成细线分隔的行、字段按列对齐 ——
2253 家企业的用途是**横向比价**，卡片网格每张只装一家、字段位置随内容长短浮动，扫不动也对不齐。
列位用**具名 grid 区域**定义一次，行与表头引用同一组名字：此前两边各写一份
`grid-template-columns`，改宽一处就整体错位。窄屏退回一条条记录，但**不丢字段**。

**④ 只有一处阴影、两级圆角。** 全站此前把 KPI、筛选器、集群、企业、名单全塞进
同一条圆角 + 同一条柔和阴影的卡里，层级完全靠不住。现在卡只留细线边界，
真正的浮起留给 `.panel`；`--r-xs`（输入框/标签）与 `--r-md`（面板）分开。

### 顺手修掉的四件事

| 问题 | 处理 |
| --- | --- |
| **`h3` 完全没有样式**（等于默认 1.17em 粗体，中文里与正文几乎一样重） | 补字重与字号，「企业档案」这类小节题才立得住 |
| **页面标题与段落标题同级**（所有页都 `<h2>` 18px） | 新增 `.page-head`（宋体、两档之差）+ `.section h2`（短引导线标出段落起点） |
| **导航 `flex:1` 挤掉检索框**（占位文字被截断） | 导航改 `min-width:0`、检索框 `margin-left:auto`；窄屏先让出次要导航项，保住两个主入口（用 `:first-child` / `:last-child` 选中首尾，而不是写 `nth-child(1)/nth-child(4)`：导航项数一变，写死的序号就会静默地隐藏错的那一项） |
| **档位标签写死三层三元表达式**（`About.vue` 那处只能认出三档，**第四档「媒体·协会」会显示成「站方整理」**，把协会来源说成我们自己整理的） | 统一走 `api.js` 的 `GRADE_LABELS`（与后端 `schemas.GRADE_LABELS` 一一对应） |

### 与数据纪律一致的两处文案

* `About.vue` 的档位卡片此前显示系统键名（`gov_open` / `site_curated`），现在显示中文标签 ——
  界面上出现内部标识符等于让用户去猜我们的实现。
* 集群行的产地空值分两种：镇街产区没写 → 「主产区待补」；**415X 赛道本来就没有单一产地** →
  「未标注产地」。写「待补」是在承诺一件永远不会发生的事（我们不会给「低空经济与航空航天」编一个产地）。
  同理，赛道集群的「产业」与集群名一字不差时整格不渲染，而不是写「—」（那会被读成「我们不知道」）。
* 核实档位只有字母时展开成「B 工商可核」（`api.js` 的 `tierLabel`）——
  「核实档位：B」对读者等于没说。

### 对外文案不提「抓取」

**站内不出现「抓取 / 爬虫 / 爬取」这类词，也不再用「已抓取校验」当标签。**
理由不只是措辞：标签要回答的是「这个值是谁给的、核到什么程度」，
而「抓取」描述的是**我们怎么做**。读者会把「已抓取」误读成「这家企业已被本站查过」——
那是我们没做过、也不该暗示的事。

| 位置 | 旧 | 新 |
| --- | --- | --- |
| 联系方式来源标签（`discovered.json`） | 自动发现 · 已抓取校验 | **站方核验 · 已比对官网** |
| 联系方式来源标签（`enriched.json`） | 站方候选 · 已抓取校验 | **站方整理 · 已比对官网** |
| 官网核验状态（`ENRICH_LABELS`） | 本站自动抓取：尚未抓取 / 抓取出错 | **官网核验：尚未核验 / 核验出错** |
| 来源声明（`/api/stats/sources`） | 须通过本站验收门才会以「已抓取校验」入库 | …以「**站方核验 · 已比对官网**」入库 |
| `/about` 时点与免责 | 抓取与核验时点见… | **核验时点**见… |

改一处不够：标签是**灌库时**从 `services/contacts.py` 的 `LAYER_LABELS` 写进
`enterprise.contact_sources` 的，所以改完必须 `seed --drop` 重灌才生效。
`tools/parse_*.py` 与 `data/curated/*_sites.json` 里的候选层说明也一并改了口径
（那些字符串会出现在数据文件里，属于对外材料）。
测试 `tests/test_api.py` 里有一条断言全库 `contact_sources` 不含这些词。

### 主营产品：一行一条，并说清「这是谁写的」

产品页此前是一个 `<ul>` 加一句「（名单原文）」。那句括注其实没有回答读者最关心的问题
（这是名单作者写的，还是你们核过的？），而产品挤成一段散文也没法拿去询价。

* 详情页改成**编号列表**，一行一条、文本可选中复制；编号在这里是真的序号
  （并列的登记品名，数得清），不是装饰性的 01/02/03。
* 说明文字写明三件事：**照录来源名单原文**、**未改写未归类**、
  它是「在该名单里登记的品类」而**不等于全部业务范围**；型号括注同样来自原文。
* **没有产品的企业不再整段消失**：改成说明「来源名单未登记主营产品」并指出
  该名单只有主体信息与地区 —— 空就是空，并写明为什么（与全站数据纪律一致）。
* 名录行里产品列**不做灰化**：一行里最深的信息应该是「这家做什么」，
  其余次要字段才是 muted。没有产品时写「未登记产品」而不是「—」。
* 「资料完整度 xx%」补上一句它由哪几项算出来（官网 / 电话 / 邮箱 / 地址 / 产品），
  否则读者看不出为什么这家 40%、那家 80%。

### 产业地图不再展示「按县汇总的家数」

`/map` 的数字带头一格原本是 `province.enterprise_count`（省 → 县汇总），
标签写「省域已收录企业 / 按县汇总」。数字本身没错，但它被排在第一位、
字号最大，读者自然拿它跟首页的「已收录企业」比 —— 于是看起来像**掉了一批企业**
（2532 掉到 1898）。用户就是这么发现的。

中间的修法曾把它并排解释（收录总数 / 已落到县级政区 / 未落到县级政区 + 一句说明），
后来又**按站方要求撤掉后两项与那句说明**（理由：那个数字既不是收录量，也不能当
覆盖率的分子——分母里那批企业根本没有地址可落）。

**撤掉之后又发现它撤得不对**：读者的第一反应本来就是「逐个点开 11 个市、把数字加起来」
（2136），再跟第一格的 2699 比。差额不写在页面上，这个矛盾就仍然由读者自己发现，
而他们的结论不会往「有 109 家没有地址」上想。所以差额曾写进第 1 格的副标题
（「其中 114 家名单未给地址…落不到县一级（地图可汇总 2512 家）」）。

**这一行最终又按站方要求撤掉了**：它解释的是我们自己的口径缝，而读者来地图是找产区，
不是来做减法；一句话带三个数字，反而让第一格读不下去。差额的算式与说明仍在
`/about` 的「口径与边界」里 —— **口径要能核对，但不必在每一页重复**：

| 格 | 数字 | 含义 |
| --- | --- | --- |
| 1 | 4228 | 已收录企业（副标签：浙江 2626 · 省外对比 1602） |
| 2~4 | 11 / 90 / 79 | 设区市 / 县级行政区 / 有产业的镇街道 |

`/about` 的「口径与边界」保留这条说明
（「地图按县级政区汇总：来源名单没给地址、企业名里也不含地名的浙江企业落不到县一级，
地图上点不到，但它们仍在企业名录里可检索 —— 地图装得下的家数不等于收录总数」）。
它是这条口径的**唯一**落点；`tests/test_tools.py` 断言地图数字带里不再出现
「落不到县一级 / 地图可汇总」，防止它被「顺手补回去」。

数字带是**固定 4 格 + 三档断点**（4 / 2 / 1 列，每种都铺满整行）。
加减格子时要同时改断点里的 `border` 规则，否则某一行会缺左边线或行线 ——
注释里写明了这一点。

### 产业集群列表可按表头排序

「集群 / 产业 / 企业数」三列的表头是按钮（`aria-sort` 跟着走，键盘可 Tab、回车可触发），
点一次升/降序，**再点一次回到默认（按档位）**。默认排序与这项功能之前完全一致
（`Cluster.tier, Cluster.name`），所以老链接不会因为排序上线而换一个顺序。

三处容易做错、也都实测过的点：

| 坑 | 表现 | 做法 |
| --- | --- | --- |
| **排序键与显示值不是同一个串** | 「按产业」排出来的顺序看着不像按产业排 | 「产业」列显示的是 `l1 · l2` 的拼接，而 **415X 赛道只有 `industry_l1`、调研派生产区只有 `industry_l2`**。只按 `l2` 排，15 条赛道（`l2` 全是空串）会一起挤在最前面，排序等于没做 |
| **`SELECT DISTINCT` 配计算列** | Postgres 直接 500：`for SELECT DISTINCT, ORDER BY expressions must appear in select list` | 排序**在 Python 侧**做（166 行，SQL 里排一次的收益抵不上把计算列 select 出来再拆包的复杂度）。底序仍是 `(tier, name)`，Python 的稳定排序天然给出 tiebreak |
| **表头在窄屏被收起来** | ≤1080px 表头 `display: none`（列位重排，留着会错位），只有表头入口的话笔记本与手机上**完全无法排序** | 筛选区同时给一个「排序方式」下拉，宽度无关。两个入口是并存的，不是二选一 |

「产业」串现在由后端算好后给出（`ClusterSummary.industry_label`），`ClusterRow` 直接渲染它 ——
**列表排序与列表显示取同一个串**，前端再拼一遍就会出现「只在一半数据上不对」的这种问题。
「主产区」与「核实程度」不给排序：前者是三个字段拼出来的文字（「杭州市」排在「金华市」
前面只是因为字形），后者是钤记标签，都不是可比的量。

排序取值由 `Query(pattern=...)` 校验，非法值 422 而不是静默回落到默认 ——
静默回落会让「点了一个不存在的排序」看起来像是排序不生效。

### 来源地图：按核实程度分组，而不是排成四列表格

`/about` 的「来源地图」此前是四列表格（档位 / 来源 / 发布主体 / 用于）。列宽一挤，
「来源」列只剩约 50px，中文名单名要折成 5 行；而「用于」列是上百字的说明，
一格里塞着半屏文字。两边都读不下去 —— 表格适合同构的短字段，这里恰恰相反。

现在改成**按核实程度分组的行**：一组的表头就是一个档位钤记加「N 份来源」，
每行第一行读完「名称 + 这份名单在库里的角色」，下面才是用途说明，占满整行宽度。
读者可以先扫档位决定要不要细读。

* 每条来源新增 `role` 字段（「集群代表企业」「产区企业层」「赛道企业池」…），
  说明它在库里承担什么。**没有 role 的行会退化成只剩一句说明长句**，
  所以 `tests/test_api.py` 有一条断言要求每条来源都给出 role。
* 说明文字里原本残留 `**加粗**`、`` `官网类型` `` 这类 Markdown 记号 ——
  页面用的是纯文本插值，这些会**原样显示出来**。库表字段名（`role 字段`、
  `source_url`、`verified_at`）同样不该出现在页面上。这两类都有断言拦。

### 来源地图旁边那张「名单口径声明」曾把九份名单写成同一档

同一页的「名单口径声明」表把每一行都写死成 `grade-official` +「官方认定」，
而九份名单里七份是第三方调研清单（站方整理）、一份是政府公开数据。
**那等于把调研方的结论说成官方认定** —— 这个站最不能出的错。
现在档位取自接口给的 `grade` / `grade_label`，与首页名单卡片同源；
`tests/test_tools.py` 里有一条扫源码的断言：视图里不得再手写 `grade-official`。

### 「我们提供的服务」与「收录不收费」必须同时在场

`/company` 在备案区块与「收录纪律与退出边界」之间新增一节「我们提供的服务」：
主办单位对外的四项业务（品牌优化 / 出海跨境独立站建设 / 长尾红人推广 / 海外 B2B 获客）。
名称在 `site.js` 的 `SERVICES` 里写一次，页面 `v-for` 渲染 —— **它是业务名称不是描述，
改一个字就是另一种说法**，所以不要在页面里再拼一遍。

**这一节的存在会让全站三处声明变得需要解释**：`/about` 的「退出边界」、本页的
「付费边界」、企业详情页页脚都写着「不收入驻费、不卖排名、不接受竞价、不做付费认证与等级背书」。
读者看到「我们提供四项服务」的第一反应会是「所以付费能进名录/能改排序」。
所以这一节**自带一句边界**，并链接到下一节：

> 这些服务与本站的收录、排序无关。……不收入驻费、不卖排名……（见下节收录纪律与退出边界）

两节的位置也是为此排的：先交代「谁在办这个站」（主办单位）→「主办单位还做什么」（服务）
→「这个站自己守什么规矩」（收录纪律）。反过来放，读者先看到四项业务再看到「不卖排名」，
两段的关联就得自己猜。`tests/test_tools.py` 里钉住了三件事：四个名称逐字在 `site.js`、
页面渲染的是 `SERVICES`、以及**「不收入驻费、不卖排名」那一句没有被服务一节顶掉**。

### 页脚备案栏只放备案要素

备案栏是**法定强制展示位**，只放主办单位全称 + ICP 号 + 公安备案号。
原先在主办单位名后还挂了一条「收录纪律与退出边界」入口链接，现已移除 ——
那段声明仍可在页脚「关于我们」列点「关于本站」到达（那才是内容入口）。

## 搜索可见性：预渲染 / sitemap / robots / 行业研究

2026-10-28 的 SEO/GEO 审计只得出一个结论：**搜索引擎和 AI 爬虫拿到的页面是空的**。
全站是客户端渲染的 SPA，nginx 对任何路径都回同一份 `index.html`，正文要等浏览器执行 JS
再向后端取数。Google 有钱渲染 JS（排队、不保证），百度 / Bing 中文 / 微博微信内搜基本不执行，
GPTBot / ClaudeBot / PerplexityBot / Bytespider 更是不执行 —— 4,000 多家企业与 200 多个集群
档案，一个字都进不了语料。

现在的分工是两层，各管一段，**不要互相替代**：

| 层 | 覆盖 | 产出 | 谁在维护 |
| --- | --- | --- | --- |
| 预渲染 | 首页 + 6 个说明/列表页 + 118 个非薄页集群 + 行业研究列表与每篇文章 | `dist/<path>/index.html` | `tools/prerender.py` |
| 页面 head | 全站 | title / description / canonical / OG / JSON-LD | `frontend/src/seo.js` 的 `applySeo` |

行业研究**不走**「后端直出整份 HTML」那条老路：它是站点的内容栏目，正文要嵌在页头 /
页脚 / 导航之间，所以由 Vue 页面渲染、靠预渲染保证可被读到（见第 4 节）。

### 1. 预渲染（`tools/prerender.py`）

```bash
cd frontend && npm run build        # 或一步到位：npm run build:seo
cd .. && .venv/bin/python tools/prerender.py
```

- 用 Playwright 打开 `vite preview`（它把 `/api` 代理到后端），等页面**真的加载完**
  再把 `page.content()` 写成 `dist/<path>/index.html`：
  `h1` 只证明「页面挂上了」，列表页的 h1 是同步渲染的，数据还在路上 ——
  所以还要等 `.loading` 占位消失，最后一页 `.loading` 还在就报「仍在加载态」，
  不静默写出一份没有数据的快照；
- 预览服务每次**现取空闲端口**并独立进程组，用完整组收掉：复用「4173 上有人在响应」
  的那个进程是陷阱 —— 它手里是旧 dist（`npm run build` 会换掉所有带哈希的文件名），
  表现成随机某一页等不到 `h1`；
- 单页失败重试一次；只想补渲染几页时用 `--only /clusters --only /enterprises`；
- URL 清单**从后端拉**（`/api/clusters` 与 `/api/research`），不手写 —— 集群增删、
  研究文章导入都是常态，
  手写清单会让「sitemap 里的 URL」与「磁盘上的产物」对不上，那正是软 404 的来源；
- **跳过薄页集群**（`is_stub`，挂载企业 < 10 家，当前 94 个）：提交一堆「集群名 + 一句话」
  的页面只会让搜索引擎判定整站质量偏低。企业数补到 10 家以上自动进来，不需要人工维护名单；
- 落盘目录要用**解码后**的路径：集群 slug 带中文（`415X-人工智能`），URL 里是百分号编码的，
  而 nginx 是解码后去文件系统找目录的。落成 `415X-%E4%BA%BA.../` 的话线上永远命不中；
- 顺带写 `dist/404.html`（`noindex`），给 nginx 的 `try_files … =404` 兜底。

**关键约束：head 里的东西只能由 `src/seo.js` 一份实现写。** 预渲染跑的是同一套 Vue 代码，
所以 `applySeo` 在预渲染时写进 HTML、在站内导航时改写 DOM，天然一致。谁再写一份
「构建时注入 meta」的逻辑，两边一定漂移，最典型的事故是预渲染 HTML 里是 A 标题、
用户进来后 JS 改成 B 标题。

详情页（集群 / 企业）拿到数据后覆盖 head：标题用真实名字（4,000 多个企业页共用一个
「企业详情 · 杭州波动粒子」等于放弃了标题），描述用页面上已有的事实拼（产业 / 产区 /
家数 / 核实档位），不写模板空话；集群页挂 `CollectionPage` + `ItemList`，企业页挂
`Organization`（**不用 `LocalBusiness`**；集团站 / 母公司站不进 `url`），`/about` 挂
`Dataset` + `FAQPage`。JSON-LD 不随页面切换残留，`applySeo(null)` 会清掉上一页那段。

### 2. `/sitemap.xml` 由库生成

`backend/app/routers/sitemap.py`：静态页 + 非薄页集群 + 已发布的研究文档。
薄页不进 sitemap（理由同上）；中文 slug 用 `quote()` 编码（XML 不接受裸中文 URL）。
不写成构建时静态文件，因为集群与企业是**灌库之后才会变**的 —— 静态文件必然滞后，
而 sitemap 唯一的价值是「列出来的 URL 一定存在」。

### 3. `robots.txt` 与 `llms.txt`

都在 `frontend/public/`（构建时原样复制到 `dist/`）。robots 挡住 `/login`、`/favorites`、
`/admin`、`/api/admin` 与 `?q=` / `?page=` 参数页；**不挡 AI 抓取器** ——
那一组正是 GEO 的入口，被白嫖的风险靠 `/api` 限流解决。`llms.txt` 写清数据口径与
机器可读接口，供 AI 引擎直接引用。

### 4. 行业研究（`/research`）

**正文嵌在站点页面里**，不是一份独立文档：`/research` 是博客列表，`/research/<slug>`
把文章正文渲染进页头 / 页脚 / 导航之间。文档由后台导入，存成文件而不是入库：

```
data/research/index.json      # 清单：slug / title / summary / published_at / updated_at / source_file
data/research/<slug>.html     # 文档原文（自带 <style>，原样保存）
```

与名单导入同一条原则（产物文件才是数据源），但**导入即生效，不需要灌库** ——
它不进数据库。接口：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/research` | 清单（JSON，公开）：标题 / 摘要 / 日期 / slug |
| `GET` | `/api/research/<slug>` | 单篇：`article` 元数据 + `body`（正文片段）+ `styles`（文档自带 CSS） |
| `GET` | `/api/admin/research` | 清单（管理视图） |
| `POST` | `/api/admin/research/import` | multipart：`file` + 可选 `slug` / `title` / `summary` / `published_at` |
| `DELETE` | `/api/admin/research/<slug>` | 下线（文件一起删，链接立刻 404） |

```bash
curl -X POST $BASE/api/admin/research/import -H "X-Admin-Token: $TOKEN" \
  -F file=@docs/浙江产业集群收录体系搭建方案.html \
  -F summary='三层数据分离、五档核实程度、集群与行政区解耦。' \
  -F published_at=2026-10-09
```

页面：`/admin/contacts` 底部的「行业研究文档」（与名单导入是两条链路，别混）。

**为什么拆 `body` / `styles` 而不是直出整份 HTML**：整份文档塞进页面会带上它自己的
`<html>` / `<head>` / `<title>`；而文档的 CSS 里有 `:root{}` / `body{}` / `*{}`，
原样注入会改掉全站排版。所以正文与样式分开返回，样式由
[researchDoc.js](frontend/src/researchDoc.js) 统一加 `.research-doc` 作用域前缀
（`@media` 递归进去、`@font-face`/`@keyframes` 原样保留），只影响文章那一块。

**两层清洗**：服务端先把 `<script>` 从正文里剥掉；前端再用 `DOMParser`（不执行脚本）
走一遍，去掉 `on*` 事件、`javascript:` 链接与 `iframe`/`object`/`embed`，然后才交给
`v-html`。之所以要两层，是因为这份内容最终进的是**同源**页面，而登录令牌就在 localStorage 里。

**slug** 允许中文（与集群 slug 同风格，`slug` 留空取文件名），但必须挡住
`/`、`..` 等路径字符，否则能写到 `data/research/` 之外。

**发布后要重跑预渲染**：页面立刻可看（前端实时取接口），但收录引擎拿到的仍是旧快照；
`npm run build:seo` 会把 `/research` 与每篇文章一起渲染进 `dist/`。新 slug 在下次预渲染
之前没有产物，nginx 用列表页骨架兜底（见第 5 节），所以不会 404。

### 5. nginx

参考配置在 `deploy/nginx.qicifier.com.conf`（**不在部署链路上**，要人工同步到服务器）。
四处必须改：`gzip`（现在 200KB+ 的 JS 是裸传的）、`robots.txt` 命中真文件、
`sitemap.xml` 反代到后端、`try_files $uri/index.html … =404`（现在不存在的路径返回 200 + 空白页）。
`/research` **不要**反代：它是站点路游，靠预渲染；只加一条「新 slug 退回列表页骨架」的
`try_files`，让后台刚导入、还没重新预渲染的文章也能打开。
`deploy/nginx.qicifier.com.conf` 文件头写了上线后的 `curl` 验收命令。

改完先确认**发布的确实是新 dist**：审计实测线上引用 `index-Dpbpy29H.js`，而本地
`dist/` 建出来是另一个哈希 —— 部署链路不同步时，所有改动都"看不见效果"，
先查这条，别怀疑代码。

### 6. 部署：三处必须一起更新（2026-10-28 线上事故）

前端产物、后端进程、nginx 配置是**三个独立的发布物**，少更新一个都会表现成
「功能坏了」，而不是「还没部署」。当天线上的真实症状与判据：

| 只更新了前端 `dist`（本次事故） | 现象 | 一条命令确认 |
| --- | --- | --- |
| 后端进程还是旧代码 | 后台导入研究文档报 **「导入失败：Not Found」**；页面有入口但打不开文章 | `curl -s https://qicifier.com/api/health` → `features` 里应有 `research`；没有就是旧后端 |

## 数据模型（对应方案 §03–§04）

| 表 | 作用 |
| --- | --- |

## 已实现的收录纪律

- **口径声明**：两份名单逐份标明发布主体与数量，页面显式声明「不可相加」。
- **镇街实体**：`/map` 支持「按镇街」检索，镇街级 URL 可访问（`/clusters/datang-waye`）。
- **规模数字**：`cluster.metrics[]` 强制五元组；未摘录到带口径数字的集群**不显示任何规模值**（禁止裸数字）。
- **称号拆分**：`honors[]` 含 `granted_by` 与 `grade`，协会称号不得进「官方认定」档。
- **核实程度**：五档（官方认定 / 政府公开信息 / 媒体·协会 / 站方整理 / 企业自报），逐条标注，不是整页一个标签。
- **站方整理隔离**：镇街块状经济显示独立「站方整理」标记，不与官方认定同款式呈现。
- **联系方式边界**：只采集官网公开的总机/400 与公开邮箱；**手机号一律不采集、不展示**；值留空而不猜测。
- **排序规则**：只按核实程度与资料完整度，对所有企业一致；不收入驻费、不卖排名、不接受竞价。
- **退出边界**：企业详情页与 `/company#policy` 明示不下单、不收款、不展示报价、不撮合、不抽成、不保证回复
  （原先只在页脚，见「口径与边界声明的位置约定」）。
- **空壳检查**：企业数 < 10 的集群标记 `is_stub`，列表与详情页双重提示，避免空壳页被当成实页。
- **备案信息**：主办单位全称 + ICP 备案号 + 公安备案号（含官方盾牌图标）集中展示在页脚，见下一节。

### 浏览器标签页标题

标签页标题形如「首页 · **杭州波动粒子**」。后缀写在两个地方，**必须一致**：

| 位置 | 作用 |
| --- | --- |
| `frontend/index.html` 的静态 `<title>` | JS 执行前 / 无 JS 时的兜底，也是搜索引擎看到的那份 |
| `frontend/src/site.js` 的 `SITE_TITLE` 常量 | 路由切换时改写 `document.title`（由 `src/seo.js` 的 `applySeo` 统一写入） |

不一致的后果很具体：首屏会先闪一下旧名字，搜索结果里会出现两个站名。

**改这个后缀要同步 `./zanzhu.sh` 的 `WEB_MARKER`** —— 它靠「`curl` 到的首页 HTML 里
有没有这串字」判断端口上跑的是不是本库前端。页面内的品牌名（顶栏「浙江产业带企业库」）
是 JS 渲染的，`curl` 抓不到，所以判据只能用静态标题里的这个后缀。

### 页脚结构（三列）

客户服务 / 网站地图 / 关于我们，下方是主体声明与备案信息栏。六条内容约定：

- **网站地图列只放通用入口**（首页 / 产业地图 / 产业集群 / 企业名录 / 关于我们），不列具体类目 —— 类目随运营增删，写死在页脚必然过期。
- **账户流（登录 / 收藏）不进页脚**：未登录点进去只会被踢回登录框，等于制造无效点击；账户入口在顶栏。
- **客户服务列直接公开联系邮箱** `contact@qicifier.com`，保证这一列每一项都点得动（邮箱是 `mailto:`，不是死文本）。
- **页脚不放订阅表单**：留资入口已撤下，改成公开邮箱，用户想联系直接写信即可。
- **关于我们列放说明性页面**，顺序为「关于本站」（`/company#about-us`）→「数据导入」（`/admin/contacts#import`）→「数据来源与核实程度」（`/about`）→「行业研究」（`/research`）。
  这个顺序是刻意的：**站是什么 → 数据怎么进来的 → 进来的数据有多可信 → 站方自己怎么看这个行业**。
  「数据导入」指向管理页的批量导入段落（导入功能一直在那里，此前没有能直达的地址）；
  `/admin/contacts#import` 的区块要解锁后才渲染，所以 `main.js` 的 `scrollBehavior`
  在目标不存在时返回 `false`（不把选择器交给 router，避免那条
  `Couldn't find element using selector` 告警），由该页在解锁后自己补滚一次。
  运营性栏目（用户故事 / 公司故事 / 公司新闻）已全部移除，页面上只留能长期维护的备案类信息。

  早先它是后端直出的独立文档，当时必须用原生 `<a>`；改成嵌入后，那条约束自然消失 ——
  现在顶部导航与页脚指的是同一个路由，两处不要一个走 `<a>`、一个走 `RouterLink`。
- **顶部导航放五个内容入口**（产业地图 / 产业集群 / 企业名录 / **行业研究** / 关于我们）：

### 口径与边界声明的位置约定

页脚**只留法定强制内容**（主办单位全称、ICP 号、公安备案号 + 盾牌图标、版权行）——
备案栏是法定展示位，不放内容入口。原先页脚底部那两段声明已整理进 `/company`
的「收录纪律与退出边界」一节，从页脚「关于我们」列的「关于本站」可达。

整理时**每一条断言的语义都不改**，只做分组（顺序照原样）：

| 分组 | 断言 |
| --- | --- |
| 收录与排序 | 以官方名单为骨架，逐条标注核实程度；排序只依据公开可核验程度与资料完整度，对所有企业一致 |
| 付费边界 | 不收入驻费、不卖排名、不接受竞价、不做付费认证 |
| 信息公开边界 | 只展示公开地址与官网公示的企业联系方式，不含任何个人联系方式 |
| 交易边界 | 本站不下单、不收款、不展示报价、不撮合、不抽成、不保证回复 |

**为什么要拆成四组**：原文是两段长句，读者会只看后半句（「不卖排名」比「以官方名单为骨架」
更容易被记住）。分组后每组只回答一个问题，也方便别处引用单条。

**页脚为什么不放这两段**：页脚是最常被截图的位置，把承诺塞在那里容易被误认成「整站声明」；
而这两段也不是备案要求展示的内容。放进「关于我们」页后语义更清楚，同时页脚保留入口链接，
不至于让人以为声明被删掉了。

**入口现在只有一个**：`/company#about-us`（页脚「关于我们」列）。原先页脚备案栏里还有一条
指向 `/company#policy` 的入口，已移除 —— 备案栏是法定展示位，只放备案要素。

**「不含任何个人联系方式」这一条三处同口径**：`/company#policy`、`/service` 的隐私条款、
`/about` 的账号与隐私。改一处必须三处一起看。

### 「关于我们」页：备案信息 + 收录纪律与退出边界

`/company` 两块内容：**主办单位**（备案全称、ICP 号、公安备案号 + 图标、联系邮箱、版权行）
与**收录纪律与退出边界**（上面那张表）。没有内容栏目。

**不要往这个页面加运营性内容。** 曾经有过「用户故事」「公司故事」「公司新闻」三节，全部移除，
原因不是内容不好，而是**页面承诺了自己维护不了的东西**：内容栏目需要持续供稿，
公司新闻要在页面与 `memory.md` 两处各维护一份变更记录（早晚不一致），
而这三节都不属于备案要求展示的内容。运营性内容一旦上线就会被截图、被引用，删也难受、留也难受。

### 对外联系方式只有一个邮箱

[`frontend/src/site.js`](frontend/src/site.js) 的 `CONTACT_EMAIL = contact@qicifier.com`（与 qicifier.cn 同主体共用），

对外再放一个私人邮箱或手机号就与自己的承诺冲突；`contact@` 是主体邮箱，不指向个人。

### 访问统计：Google Analytics 4

衡量 ID `G-CBYH25YPBK`，**只写在 [`frontend/index.html`](frontend/index.html) 一处**，

四条实现约束（改动前先读这段）：

| 本地开发 / 预览**不加载** | 都跑在 `127.0.0.1`。本机调试会把生产报表灌满假会话，而且这些数据事后删不干净 |
| 尊重 `Do Not Track` | 浏览器明确要求不被跟踪时不加载。这是用户表达过的意愿，不该由我们替他决定 |
| **首屏与站内跳转都由路由发 `page_view`** | 这是 SPA：GA4 的自动上报只在首次加载发一次，站内跳转（`/clusters` → `/enterprises`）它看不到。所以 `config` 里设了 `send_page_view: false`，再由 `main.js` 的 `router.afterEach` 统一上报 —— 两者只留一边，否则首屏会被记两次 |
| **不上报账号标识** | 没有 `user_id`，也没有自定义维度。隐私条款承诺「账号信息不与第三方共享」，一旦加上，报表就能把浏览行为关联到具体某个人 |

`/admin/*` 不计入统计：它是站方自己的维护入口，混进来会污染「公众访问量」这个口径。

### 本站不参与交易 ⇒ 页面上不写配送与退换

「客户服务」页**刻意不含**配送说明、退换政策这类内容：本站不下单、不收款、不撮合，
写配送时效或退换承诺等于自认是销售方，与公开承诺矛盾，也会引来本不该存在的售后请求。
该页只有两块：**隐私条款**与**联系我们**（联系邮箱 + 更正通道 + 备案信息 + 服务范围）。
